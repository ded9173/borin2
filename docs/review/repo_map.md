# Карта репозитория Borin

## Назначение проекта
По именам модулей и моделей это Flask-приложение для учёта контрагентов, номенклатуры, цен/себестоимости, заказов, спецификаций, пользователей и заметок. Полное бизнес-описание отсутствует: `README.md` содержит только `Python 3.14`.

## Структура
- `run.py` — точка запуска Flask.
- `app/__init__.py` — фабрика приложения, загрузка `.env`, расширения, регистрация Blueprint, обработчики ошибок и `db.create_all()`.
- `app/config.py` — конфигурационные классы и формирование URL PostgreSQL.
- `app/extensions.py` — SQLAlchemy, Flask-Migrate, Flask-Login.
- `app/models.py` — ORM-модели.
- `app/blueprints/` — функциональные HTTP Blueprint (auth, customer, items, orders, notes, specification, admin, web, captcha).
- `app/views/` — альтернативный слой class-based API views.
- `app/services/` — бизнес-логика.
- `app/repository/` — доступ к данным.
- `app/dto/` — DTO.
- `app/auth.py`, `app/utils.py`, `app/puzzle_captcha.py` — вспомогательная логика.
- `database/db.sql` — DDL PostgreSQL, индексы и внешние ключи.
- `web/` — HTML-шаблоны и клиентский JavaScript.
- `image/` — изображения для интерфейса/капчи.
- `docs/review/` — отчёты ревью (в том числе подготовленные в рамках этой проверки).
- `.env` — локальные настройки; содержит секретоподобные значения и не должен публиковаться.
- `.idea/` — настройки IDE.

## Отсутствующие артефакты
В архиве отсутствуют `tests/`, `scripts/`, `postman_collection.json`, `er_diagram.pdf` и непустой `requirements.txt`. Каталог `database/` присутствует, в нём находится `db.sql`. Git-метаданные `.git/` отсутствуют, поэтому коммиты из этого архива создать нельзя.

## Архитектурная схема (задуманная по именам каталогов)
`run.py` → `app.create_app()` → Blueprint / views → services → repositories → SQLAlchemy models → PostgreSQL.
Фактическая реализация непоследовательна: часть endpoint находится в `app/blueprints`, часть — в `app/views`; некоторые импорты и связи слоёв указывают на несуществующие объекты/модули. Поэтому схема отражает предполагаемое разделение, а не подтверждённый сквозной поток.

## Вывод
Основные слои выделены, но присутствуют параллельные реализации API и несогласованное именование. Перед дальнейшей разработкой следует выбрать один подход к маршрутам (Blueprint или class-based views), унифицировать модели/DTO/сервисы/репозитории и добавить воспроизводимые инструкции и тесты.
